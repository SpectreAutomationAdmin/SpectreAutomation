# Spectre navigation discoverability audit

Generated by `npm run nav:audit`. Re-run after every meaningful UI
change. The non-technical-founder requirement is that **no user-facing
route should require typing a URL or remembering a file path**.

## Status

| Bucket | Count |
|---|---|
| Total page routes | 133 |
| Linked in sidebar | 76 |
| Linked from a parent page (list/detail row, hub card) | 11 |
| URL-only (orphan) | **0** |
| Internal / deliberately allowlisted | 46 |

The audit script (`scripts/nav-audit.ts`) crawls every `page.tsx` under
`src/app/app/` and scans the rest of the source tree for any
`href="<route>"` or `redirect("<route>")` reference. A route counts as
discoverable when either the sidebar lists it, the route appears in a
non-self link in the codebase, or one of its parent routes does.

The script exits non-zero when any URL-only orphan is found, so CI can
later block PRs that introduce one.

## Bucket definitions

- **LINKED FROM NAV** — the route is in the persistent sidebar
  ([src/components/Sidebar.tsx](../src/components/Sidebar.tsx)). The
  founder reaches it in one click from any page in the app.

- **LINKED FROM PARENT** — the route is reachable via a link on its
  parent (e.g. AP invoice rows link to `/ap/invoices/[id]`, the
  Hospitality hub links to the Floor Map, the reservation list page
  has a "Floor view" button). The sidebar does not need to list every
  detail / sub-form page.

- **URL-ONLY** — nothing in the app links here. The founder would have
  to know the route. **This bucket must stay empty.** When this list
  grows, the navigation has regressed and the responsible task is not
  done.

- **INTERNAL / ALLOWLISTED** — the route is deliberately not in the
  founder-facing nav. Common reasons:
    - Dynamic detail routes whose parent list IS in nav
      (e.g. `/admin/members/[id]` reached from `/admin/members`)
    - Sub-forms (e.g. `/gl/new`, `/coa/new`) reached from the parent
      list with a "+ New" button
    - Super-admin-only platform pages already gated SUPER_ONLY
    - Member-side detail / receipt routes opened from email links
  The allowlist lives at the top of `scripts/nav-audit.ts`.

## How to keep this audit at zero orphans

`npm run nav:audit` runs in <2 seconds locally. The expectation per
[CLAUDE.md](../CLAUDE.md):

> Every new user-facing route must be discoverable through the UI
> before the task is complete. A feature is not done if a user must
> know the URL or file path to access it.

Concretely, when adding a new page:

1. **Pick the right home.** Add to the persistent Sidebar
   ([src/components/Sidebar.tsx](../src/components/Sidebar.tsx)) **if**
   it's a top-level workflow (Reservations, Inventory, Reports). Add a
   module card on the relevant hub page (e.g. `/app/admin/hospitality`,
   `/app/admin/ops`) **if** it's a sub-feature of an existing area.

2. **Wire the permission.** Use the same permission key as the page's
   server-side guard. The sidebar hides items the user can't access;
   the audit script doesn't care about permissions, only that the link
   exists in the codebase.

3. **Run `npm run nav:audit`.** A zero URL-only count means done.
   A non-zero count is a regression — either add the link or, if the
   route is genuinely detail-only and reached via a row click, add it
   to the `INTERNAL_ALLOWLIST` at the top of `scripts/nav-audit.ts`
   with a one-line reason in the comment.
